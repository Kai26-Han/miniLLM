# Fine-tuning：主流方案解析

> Fine-tuning（微调）的价值不是“把文档背进模型”，而是用领域数据改变模型的稳定行为：让它更可靠地遵循任务协议、输出固定格式、使用专业表达、调用工具，或把大模型能力迁移到更小、更便宜的模型中。

## 关键点

1. **先判断问题属于知识、行为还是能力。** 动态知识优先用 RAG，流程动作优先用工具，稳定行为和任务能力才是 Fine-tuning 的优势区间。
2. **业务上最常见的是 SFT + LoRA/QLoRA。** SFT 定义学习目标，LoRA/QLoRA 决定以更低成本更新多少参数；两者不是互斥方案。
3. **全参数微调不是默认答案。** 它容量大、部署直接，但训练、存储、回滚和多租户成本都更高。
4. **持续预训练与 SFT 解决不同问题。** 前者学习领域语言和分布，后者学习“收到什么输入时应该怎样输出”。
5. **数据质量和评测闭环通常比训练技巧更重要。** 错误示范、标签矛盾和评测泄漏会被模型稳定地学进去。
6. **Fine-tuning 不能替代外部事实源。** 高频变化的价格、库存、政策和账户状态应在推理时读取，而不是固化在权重中。
7. **先建立不训练的基线，再启动微调。** 没有 Prompt/RAG 基线，就无法判断训练收益是否值得持续承担模型生命周期成本。
8. **上线的是一套版本化系统。** 基座模型、Tokenizer、Chat Template、Adapter、数据、代码、评测集和推理参数必须一起管理。

---

## 1. Fine-tuning 到底改变了什么

预训练模型已经学习了通用语言、知识和模式。Fine-tuning 从这个检查点继续训练，通过更小、更有目的的数据集更新全部或部分参数，使条件分布从：

\[
p_{\theta_0}(y\mid x)
\]

变成更符合业务目标的：

\[
p_{\theta}(y\mid x,\text{业务规范})
\]

它最擅长改变四类稳定属性：

- **任务协议**：分类、抽取、改写、摘要、问答、工具调用；
- **输出结构**：JSON Schema、固定字段、SQL、DSL、代码补丁；
- **表达习惯**：术语、语气、长度、拒答边界和品牌风格；
- **效率结构**：让小模型模仿大模型，以更低延迟和成本处理窄任务。

Fine-tuning 并不是数据库写入。权重中的知识不可精确寻址、难以删除、没有来源引用，也不能保证按时间更新。因此，“让模型记住最新产品价格”通常是错误目标，“让模型学会根据检索到的产品资料生成合规答复”才是合适目标。

## 2. 先做问题归因：Prompt、RAG、工具还是 Fine-tuning

业务需求经常被笼统描述成“模型不够懂我们”。实际应拆成以下问题：

| 需求 | 首选方案 | 原因 |
|---|---|---|
| 固定角色、语气、少量规则 | System Prompt / Few-shot | 修改快，无训练和模型维护成本 |
| 查询内部文档、最新政策、商品信息 | RAG | 内容可更新、可引用、可做权限控制 |
| 查询库存、下单、计算、调用内部系统 | Tool Calling / Workflow | 结果来自确定系统，而不是模型记忆 |
| 稳定输出 JSON、分类标签或领域格式 | SFT | 大量示例可把行为固化为模型习惯 |
| 学习行业语言、代码库分布或罕见术语 | 持续预训练 + SFT | 先补领域表示，再学习具体任务 |
| 在多个可行答案中学习偏好 | DPO / RLHF | 目标是相对好坏，不是唯一标准答案 |
| 把高质量大模型替换成低成本小模型 | 蒸馏 + SFT | 用 Teacher 生成监督数据迁移能力 |
| 数学、代码等可自动判断成败的任务 | 强基座 + SFT + 强化微调 | 可用执行器或规则提供密集反馈 |

这几种技术可以组合：

```text
用户请求
  ↓ Prompt 定义角色与边界
检索系统提供当前事实
  ↓
微调模型按业务格式推理和组织答案
  ↓ Tool 调用真实业务系统
规则、权限与安全层校验输出
```

一个实用原则是：

> 需要频繁更新、精确引用或权限隔离的信息放在模型外；需要高频复现、稳定泛化的行为才写入模型参数。

## 3. “微调”包含哪些主流训练阶段

### 3.1 持续预训练：让模型适应领域分布

Continued Pretraining 也常被称为 Domain-Adaptive Pretraining（DAPT）或 Mid-training。它使用大量未标注领域语料，继续优化 Next-token Prediction：

\[
L_{CPT}=-\sum_t\log p_\theta(x_t\mid x_{<t})
\]

适合：

- 法律、医疗、金融、科研等专业文本分布与通用互联网明显不同；
- 存在大量未标注语料，但高质量问答对较少；
- 需要补充行业术语、固定文体、代码库或小语种表示；
- 需要训练新的上下文长度、Tokenizer 扩展或特殊数据格式。

局限是它不会自动教会模型对话、拒答或任务格式。通常还要接 SFT；若领域数据单一，也要混入通用数据以减轻灾难性遗忘。

### 3.2 SFT：让模型模仿目标回答

Supervised Fine-Tuning 使用输入—目标输出对。设上下文为 \(x\)，回答为 \(y=(y_1,\ldots,y_T)\)：

\[
L_{SFT}=-\sum_{t=1}^{T}\log p_\theta(y_t\mid x,y_{<t})
\]

对话训练通常只让 Assistant 区域参与 Loss，System、User、Tool Result 只作为条件。这是企业定制最常用的训练目标。

SFT 适合“可以示范正确答案”的场景：如果专家能写出理想输出，模型就可以直接模仿；如果专家只能说 A 比 B 好，却难以写出唯一标准答案，则偏好优化更合适。

### 3.3 偏好与强化阶段：让模型优化“更好”

SFT 之后还可以使用 chosen/rejected 偏好对、Reward Model 或可验证 Grader 继续训练。严格来说这些属于 Preference Optimization 或 Reinforcement Fine-tuning，详见同目录的《RLHF：业务主流方案解析》。

### 3.4 蒸馏：把能力迁移到更小模型

蒸馏的常见业务流程是：

1. 收集真实请求或构造覆盖业务分布的 Prompt；
2. 让能力更强的 Teacher 生成回答、推理或工具轨迹；
3. 用规则、执行器、LLM Judge 和人工抽检过滤；
4. 对较小 Student 进行 SFT，必要时再做偏好优化；
5. 比较质量、延迟、吞吐和单次请求成本。

蒸馏不是简单复制所有 Teacher 输出。未经验证的数据会把幻觉、冗长和单一表达一并迁移给 Student。

## 4. 参数怎么更新：全参数、LoRA 与 QLoRA

训练目标和参数更新方式是两个维度。SFT、DPO 等目标都可以搭配全参数训练或 PEFT。

### 4.1 全参数 Fine-tuning

更新模型全部参数：

\[
\theta\leftarrow\theta-\eta\nabla_\theta L
\]

优点：

- 可调整容量最大，适合数据充分且分布变化较大的任务；
- 最终权重完整，部署时不需要挂载 Adapter；
- 大规模训练下通常更容易达到能力上限。

代价：

- 梯度和优化器状态显著增加显存；
- 每个业务版本都要保存完整模型；
- 小数据更容易过拟合或破坏通用能力；
- 多租户、频繁迭代和快速回滚成本高。

它更适合模型提供方、单一高价值模型、大规模高质量数据，或 LoRA 容量已被实验证明不足的场景。

### 4.2 LoRA：主流参数高效微调

LoRA 冻结原权重 \(W_0\)，只学习一个低秩增量：

\[
W=W_0+\Delta W,\qquad \Delta W=BA
\]

其中 \(A\in\mathbb{R}^{r\times d}\)、\(B\in\mathbb{R}^{k\times r}\)，且 \(r\ll\min(d,k)\)。训练参数从 \(kd\) 降为约 \(r(d+k)\)。

LoRA 的业务优势包括：

- Adapter 文件小，便于版本管理和按客户隔离；
- 可以共享一份基座，在请求间切换不同 Adapter；
- 训练所需优化器状态和梯度更少；
- 可以在部署前把 Adapter 合并回基座，避免额外推理算子。

常见超参数：

| 参数 | 含义 | 主要影响 |
|---|---|---|
| `r` | 低秩维度 | 越大容量越高，参数和显存也越多 |
| `lora_alpha` | 增量缩放 | 控制 Adapter 更新强度 |
| `target_modules` | 注入层 | 决定可调整的模型子空间 |
| `lora_dropout` | Adapter Dropout | 小数据时帮助正则化 |

工程上应先用普通 LoRA 建立基线，再通过消融判断是否需要提高 Rank、覆盖全部 Linear 层或使用 LoRA 变体。变体更多并不自动意味着业务效果更好。

### 4.3 QLoRA：量化基座上的 LoRA 训练

QLoRA 将冻结基座以 4-bit 等低精度形式加载，梯度穿过量化权重，只更新 LoRA 参数。它大幅降低基座权重占用，让较大模型可以在更少 GPU 上训练。

需要注意：

- “4-bit 加载”主要节省基座权重显存，激活、LoRA 梯度和优化器仍然存在；
- 量化误差可能影响对数概率、细粒度生成和训练稳定性；
- 训练完成后要明确部署的是量化基座 + Adapter，还是合并并重新量化的权重；
- QLoRA 是资源受限时的强基线，不是所有质量目标下都等价于全参数训练。

### 4.4 其他 PEFT

Adapter、Prefix Tuning、Prompt Tuning、IA3 等方法也能减少训练参数，但在通用 LLM 业务中，LoRA 生态、工具链和部署支持通常更成熟。除非已有平台约束或实验明确受益，优先从 LoRA 开始。

### 4.5 业务选型对照

| 方案 | 训练显存 | 单任务产物 | 质量容量 | 多租户 | 典型选择 |
|---|---:|---:|---:|---:|---|
| 全参数 SFT | 高 | 完整模型 | 高 | 差 | 大数据、单一核心模型 |
| LoRA SFT | 中低 | 小 Adapter | 中高 | 好 | 企业定制默认起点 |
| QLoRA SFT | 低 | 小 Adapter | 中高 | 好 | GPU 受限、快速验证 |
| Prompt/Prefix Tuning | 低 | 极小参数 | 较受限 | 好 | 特定平台或简单任务 |
| 持续预训练 + SFT | 很高 | 完整模型或 Adapter | 高 | 一般 | 强领域迁移 |
| 蒸馏 + SFT | Teacher 推理 + 训练 | 小模型 | 取决于 Teacher 与过滤 | 好 | 降低线上成本和延迟 |

## 5. 六类常见业务方案

### 5.1 结构化抽取、分类与路由

示例：工单分类、合同字段抽取、风险标签、意图路由。

推荐：

```text
强 Prompt 基线
  -> SFT + LoRA
  -> JSON Schema / 枚举约束
  -> 规则校验与失败重试
```

重点指标是字段级 Precision/Recall/F1、Schema 合法率、拒识率和长尾类别召回，而不是只看生成 Loss。

### 5.2 品牌客服与企业写作

示例：固定语气、回复长度、品牌用词、政策性拒答。

推荐使用高质量人工示范做 SFT，再用偏好对修正“都正确但风格不同”的回答。动态政策和账户信息仍由 RAG/Tool 提供。

### 5.3 领域知识助手

示例：法律检索、医疗文献、设备运维、企业知识库。

推荐组合：

```text
RAG 负责事实、来源和更新
SFT 负责术语、引用格式和答案组织
必要时持续预训练负责领域语言分布
```

仅靠 SFT 注入文档通常难以追踪来源，也不便执行删除、权限和时效控制。

### 5.4 Tool Calling 与 Agent

训练样本应包含：何时调用工具、选哪个工具、参数如何生成、如何读取 Tool Result、何时停止，以及工具失败后的恢复路径。

业务评测要在沙箱环境中运行，至少记录：

- 工具选择准确率；
- 参数 Schema 合法率；
- 完整任务成功率；
- 平均调用次数和端到端延迟；
- 越权调用、重复调用和失败恢复率。

只评估工具 JSON 的文本相似度，会漏掉“格式不同但执行正确”和“格式正确但业务错误”两种情况。

### 5.5 代码、SQL 与企业 DSL

如果有代码仓、查询日志和测试环境，可用持续预训练学习分布，用 SFT 学习任务格式，用编译器、单元测试、SQL 沙箱或静态分析作为评测与过滤器。

不要直接执行模型生成的高权限代码或 SQL。训练提升的是成功概率，不会取消沙箱、最小权限和审计要求。

### 5.6 大模型蒸馏到小模型

当线上请求集中在狭窄任务时，常见路线是“强模型生成 + 小模型微调”。业务收益来自：

- 更低首 Token 延迟和更高吞吐；
- 更短 Prompt，减少重复规则 Token；
- 私有化部署和边缘部署；
- 用固定算力服务更多请求。

应以总拥有成本评估，包括 Teacher 数据生成、人工审核、Student 训练、独立部署、持续回归和重训，而不只比较单次推理价格。

## 6. 数据工程决定大部分上限

### 6.1 数据来源

| 来源 | 优势 | 主要风险 |
|---|---|---|
| 专家示范 | 准确、边界清楚 | 贵、规模小、风格可能单一 |
| 历史业务数据 | 贴近真实分布 | 隐私、旧流程、标签噪声 |
| 用户与客服对话 | 覆盖真实问题 | 低质回答、授权和 PII |
| Teacher 合成 | 扩量快、可覆盖长尾 | 幻觉、模板化、自我复制 |
| 规则或程序生成 | 格式稳定、可验证 | 分布过于理想化 |

合成数据的正确公式不是“生成即训练”，而是：

```text
种子任务 -> 多样化生成 -> 硬规则校验 -> Verifier/LLM Judge
         -> 去重与难度分层 -> 人工抽检 -> 进入训练集
```

### 6.2 数据 Schema

建议每条样本除消息外保留元数据：

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ],
  "task": "contract_extract",
  "source": "expert_v2",
  "language": "zh-CN",
  "quality": 0.94,
  "policy_version": "2026-08",
  "document_id": "..."
}
```

元数据用于切分、重采样、问题追踪和删除请求，一般不直接拼进模型输入。

### 6.3 质量检查

- Chat Role 顺序与模板合法；
- Assistant 目标不为空，Loss Mask 不错位；
- JSON、工具参数、代码和引用可解析；
- 去除 PII、密钥、访问 Token 和无授权内容；
- 对 Prompt、Response 和完整对话做精确/近似去重；
- 排查与测试集、公开 Benchmark 和未来评测样本的重叠；
- 统计语言、任务、长度、拒答、来源和难度分布；
- 对自动 Judge 做人工校准，而不是把 Judge 分数视为事实。

### 6.4 数据切分

随机按行切分经常造成泄漏。更可靠的切分键包括客户、文档、会话、时间、模板族和任务族。

至少保留三类集合：

1. **Train**：用于参数更新；
2. **Validation**：选择超参数和停止点；
3. **Test/Golden Set**：只在候选模型冻结后评估。

再额外维护长尾集、安全集、对抗集和线上回放集，防止平均分掩盖关键失败。

## 7. 训练配方中的关键工程问题

### 7.1 基座模型选择

先选择零样本/少样本已经接近目标、许可证满足要求、部署栈支持的最小模型。微调通常擅长放大已有能力，不擅长从极弱基座凭少量样本创造复杂能力。

候选基座要在同一业务集上比较：质量、语言、上下文、工具能力、吞吐、显存、许可证和社区支持。

### 7.2 Chat Template 必须一致

训练和推理必须使用相同的：

- Role 名称与消息边界；
- BOS/EOS 和 Assistant 结束标记；
- System Prompt 放置方式；
- Tool Call / Tool Result 结构；
- Generation Prompt；
- Reasoning 内容是否可见、是否参与 Loss。

模板错位会表现为无法停止、角色串线、复读、工具 JSON 失效或整体能力突然下降。

### 7.3 学习率、Epoch 与有效 Batch

更大 Epoch 不等于更强模型。小而重复的数据很容易让训练 Loss 继续下降、业务泛化却变差。建议保存多个 Checkpoint，并以业务评测选点。

有效 Batch Size 为：

\[
B_{global}=B_{device}\times N_{device}\times N_{accumulation}
\]

比较实验时应同时记录目标 Token 数、数据采样权重、学习率计划、精度、随机种子和实际更新步数。

### 7.4 Padding、Packing 与截断

- 长度分桶和 Dynamic Padding 可减少无效计算；
- Packing 可把多个短样本拼进同一窗口，但要阻断跨样本注意并正确处理 Loss Mask；
- 长对话截断应保留 System、最近请求和目标答案；
- 记录 Prompt 截断率与 Answer 截断率，避免悄悄训练残缺目标。

### 7.5 灾难性遗忘

典型缓解方式：

- 降低学习率、训练轮数或 LoRA Rank；
- 混入通用指令数据与安全数据；
- 使用 PEFT 限制更新范围；
- 在训练中持续跑通用能力回归；
- 以路由或多 Adapter 隔离冲突任务。

如果两个业务域要求互相矛盾的格式或策略，强行合并成一个 Adapter 可能不如显式路由。

## 8. 评测：训练 Loss 不是业务 KPI

评测应形成四层结构：

| 层级 | 关注点 | 示例 |
|---|---|---|
| 格式层 | 输出能否被系统消费 | JSON 合法率、Schema 通过率 |
| 任务层 | 任务本身是否正确 | F1、Exact Match、Pass@k、执行成功率 |
| 行为层 | 是否符合人类偏好 | 盲测胜率、完整性、语气、安全性 |
| 系统层 | 上线是否值得 | P95 延迟、吞吐、单请求成本、失败率 |

推荐流程：

```text
固定基线
  -> 离线自动指标
  -> 人工盲测 / 校准后的 LLM Judge
  -> 安全与对抗测试
  -> 小流量 Shadow / A/B
  -> 监控、回滚和数据回流
```

LLM Judge 应随机打乱候选顺序，控制长度偏好，并用人工样本测一致性。关键业务不能只依赖单一 Judge。

## 9. 部署主流方案

### 9.1 托管 Fine-tuning API

优点是基础设施简单、训练和推理接口统一；局限是模型、超参数、数据驻留、版本寿命和导出能力由平台决定。

适合快速验证和团队工程资源有限的场景。选型时要确认：

- 数据是否用于平台训练、保存多久、位于哪个区域；
- 是否支持 SFT、Preference 或 Reinforcement；
- 模型是否可导出，基座下线时如何迁移；
- 训练、存储、专属吞吐和推理分别如何收费；
- 是否支持 VPC、KMS、审计、删除和权限隔离。

### 9.2 开源模型自托管

常见工具链包括 Transformers、PEFT、TRL、DeepSpeed、FSDP、vLLM 等。优势是训练与部署可控、权重可拥有；代价是需要处理分布式训练、内核兼容、监控、容灾和安全。

### 9.3 Adapter Serving

多个业务共享基座、每个业务挂载独立 LoRA：

```text
Base Model
  ├─ Adapter：客服
  ├─ Adapter：合同抽取
  ├─ Adapter：SQL
  └─ Adapter：客户 A 专属风格
```

它适合多租户，但要评估 Adapter 热加载、批处理碎片、KV Cache、路由错误和版本组合复杂度。高流量固定任务可把 Adapter 合并成独立权重，换取更简单的推理路径。

## 10. 成本模型

Fine-tuning 的总成本可粗略拆成：

\[
C_{total}=C_{data}+C_{train}+C_{eval}+C_{serve}+C_{maintain}+C_{risk}
\]

- \(C_{data}\)：专家、标注、合成推理、清洗与隐私处理；
- \(C_{train}\)：GPU、失败重跑、实验和 Checkpoint 存储；
- \(C_{eval}\)：人工盲测、Judge、红队和线上实验；
- \(C_{serve}\)：推理实例、Adapter 管理、延迟与吞吐；
- \(C_{maintain}\)：基座升级、重训、回归和数据删除；
- \(C_{risk}\)：错误输出、合规事件和供应商锁定。

微调的收益通常来自质量提高、Prompt 缩短、使用更小模型、减少重试和人工复核。要用完整链路的单位任务成本计算 ROI，而不是只看训练账单。

## 11. 推荐的最小业务闭环

```text
1. 定义单一、可衡量的业务目标
2. 固定 Prompt / RAG / Tool 基线
3. 建立独立 Golden Set 与安全回归集
4. 收集并清洗高质量示范
5. 用 LoRA SFT 训练第一个候选模型
6. 与基线比较质量、延迟和成本
7. 分析失败类型，而不是盲目加数据
8. 对高价值失败补数据或进入偏好优化
9. 小流量上线，保留路由回旧模型的能力
10. 只把经过审核的线上样本回流到下一版本
```

默认起点可以概括为：

> 选择已经较强的最小基座，用高质量数据做 LoRA SFT，以真实业务 Golden Set 选 Checkpoint；只有在证据显示容量不足时，才升级到更大基座、持续预训练或全参数训练。

## 12. 常见误区

1. **用 Fine-tuning 替代 RAG。** 结果不可引用、难更新，也无法保证记忆准确。
2. **先训练再想指标。** 没有固定基线和测试集，训练成功也无法证明业务收益。
3. **把历史模型回复直接当标签。** Student 会继承旧系统的幻觉和流程错误。
4. **训练与推理模板不一致。** 这是最常见且最隐蔽的工程失败之一。
5. **只看平均分。** 关键客户、安全长尾和工具越权可能被平均值掩盖。
6. **默认数据越多越好。** 重复、矛盾和低质量数据会稳定拉低模型。
7. **默认 LoRA 永远等于全参数。** LoRA 是强基线，但容量是否足够要靠消融确认。
8. **忽略基座升级成本。** 新基座的 Tokenizer、模板和行为变化可能要求重建数据与评测。
9. **把自动 Judge 当绝对真值。** Judge 也存在偏差、位置效应和被攻击的可能。
10. **没有回滚路径。** 模型版本、数据版本和推理配置必须能够一起回退。

## 13. 一页选型结论

| 如果你的主要问题是…… | 优先尝试 |
|---|---|
| Prompt 太长、格式经常不稳 | SFT + LoRA |
| 需要回答最新私有资料 | RAG，必要时再加 SFT |
| 需要稳定调用内部系统 | Tool Calling SFT + 执行校验 |
| 只有大量未标注领域文本 | 持续预训练，再做 SFT |
| GPU 很少但想训练较大模型 | QLoRA |
| 数据规模大且要求能力上限 | 全参数 Fine-tuning |
| 同一基座服务多个客户/任务 | 多 LoRA + 路由 |
| 大模型效果好但线上太贵 | Teacher 蒸馏到小模型 |
| 无法写唯一答案，只能比较好坏 | DPO / RLHF |
| 输出可由程序自动验证 | SFT + 强化微调 / RLVR |
