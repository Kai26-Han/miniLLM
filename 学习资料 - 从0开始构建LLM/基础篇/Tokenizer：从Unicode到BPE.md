# 分词器：从 Unicode 到 BPE

## 什么是分词器

分词器是文本与语言模型之间的翻译层：它先用 UTF-8 把任意 Unicode 文本转换为字节，再通过字节对编码（BPE）把高频相邻字节逐步合并成更大的 token，从而在词表大小、序列长度、计算成本和模型能力之间取得平衡。

## 关键点

1. **语言模型处理的不是字符串，而是 token ID。** 文本必须先经过 `encode()`，生成结果也必须经过 `decode()` 才能还原为文本。
2. **分词器和语言模型是两个独立系统。** 二者可以使用不同训练集、不同训练算法，并在不同阶段训练。
3. **BPE 通过反复合并最高频相邻 token 来压缩序列。** 每次合并都会增加一个词表项。
4. **BPE 的词表不是一组互不相关的字符串，而是一片由合并规则形成的二叉树森林。** 后期 token 可以依赖早期 token。
5. **词表越大，文本通常越短，但 Embedding、输出层和 Softmax 越昂贵。** 词表大小是重要超参数。
6. **分词训练语料决定不同数据类型的 token 密度。** 某种语言或代码出现得越多，通常越容易形成较长 token。
7. **很多模型怪异行为来自分词。** 拼写、字符串反转、整数运算、多语言、缩进和尾随空格都会受到影响。
8. **特殊 token 不属于普通 BPE 合并。** 它们由额外逻辑识别，用来表达文档边界、消息边界或控制信息。
9. **更换或扩展分词器会改变模型结构。** 至少要同步调整输入 Embedding 和输出语言模型头。

---

## 1. 分词器位于系统的什么位置？

完整信息流如下：

```text
原始文本
  ↓ encode
token ID 序列
  ↓ Embedding
向量序列
  ↓ Transformer
下一个 token 的 logits
  ↓ 采样
新 token ID
  ↓ decode
可读文本
```

分词器需要提供两个基本函数：

```python
ids = tokenizer.encode(text)  # str -> list[int]
text = tokenizer.decode(ids)  # list[int] -> str
```

理想情况下，对于任意有效字符串，都应该满足：

```python
tokenizer.decode(tokenizer.encode(text)) == text
```

但反方向不一定成立。任意整数序列未必对应有效 UTF-8 字节流，因此：

```python
tokenizer.encode(tokenizer.decode(ids)) == ids
```

并不能对所有 `ids` 保证成立。

## 2. 为什么字符级分词不够？

最简单的方案，是收集训练文本中的所有字符，为每个字符分配一个整数：

```python
chars = sorted(set(text))
stoi = {ch: i for i, ch in enumerate(chars)}
itos = {i: ch for i, ch in enumerate(chars)}
```

这种方法适合教学，但不适合开放世界文本：

- 训练集未出现的字符无法编码；
- 世界上存在大量文字、符号和表情；
- Unicode 标准仍在增加新码点；
- 不同语言的字符集合差异很大；
- 逐字符序列较长，浪费上下文窗口。

直接把每个 Unicode 码点作为 token 也不理想：词表非常大、标准会演化，而且许多码点在训练数据中极少出现，难以充分训练对应向量。

更稳妥的起点是字节，因为任意 Unicode 文本都能稳定地编码为字节流。

## 3. Unicode、码点与 UTF-8

### 3.1 Unicode 码点

Unicode 为字符分配整数码点。在 Python 中可以查看单个字符的码点：

```python
ord("A")       # 65
ord("你")      # 20320
chr(20320)     # '你'
```

码点只是字符编号，不是它在文件或网络中的实际字节表示。

### 3.2 UTF-8 编码

UTF-8 将每个码点转换为 1～4 个字节：

```python
raw = "你好，LLM".encode("utf-8")
ids = list(raw)
```

ASCII 范围内的字符通常只占一个字节，其他字符可能占多个字节。UTF-8 的优点包括：

- 能表示整个 Unicode 字符集；
- 与 ASCII 兼容；
- 互联网生态支持广泛；
- 字节范围固定为 `0～255`；
- 不会出现真正的未知字符，只要保留字节回退能力就能编码。

### 3.3 为什么不直接使用 UTF-8 字节？

若一个字节就是一个 token，则词表只有 256 项，输入和输出层都很小；但文本会被展开成非常长的序列。

Transformer 的标准注意力开销近似为：

$$
O(T^2)
$$

其中 $T$ 是 token 数量。序列被字节展开后，注意力成本和上下文消耗会迅速增加。

目标因此变成：

> 保留 UTF-8 的完备性，同时把常见字节组合压缩成更大的 token。

BPE 正是完成这项工作的算法。

---

## 4. BPE 的核心思想

假设初始序列为：

```text
A A B C A A B D A A B
```

初始词表只有：

```text
{A, B, C, D}
```

若 `AA` 是出现次数最多的相邻对，就创建新 token `Z = AA`：

```text
Z B C Z B D Z B
```

词表从 4 个增加到 5 个，序列则变短。接下来继续统计新的相邻对，重复：

```text
统计相邻对
  ↓
选择出现次数最多的一对
  ↓
创建新 token
  ↓
替换所有不重叠的匹配
  ↓
直到达到目标词表大小
```

应用到字节级 BPE 时：

- 初始 token ID 为 `0～255`，分别代表单个字节；
- 第一次合并产生 token `256`；
- 第二次合并产生 token `257`；
- 持续合并，直到达到目标词表大小。

每个新 token 都由两个已有 token 拼接而成，因此后期合并可以引用早期合并结果。

---

## 5. 第一步：统计相邻 token 对

```python
def get_stats(ids, counts=None):
    counts = {} if counts is None else counts

    for pair in zip(ids, ids[1:]):
        counts[pair] = counts.get(pair, 0) + 1

    return counts
```

输入：

```python
ids = [1, 2, 1, 2, 3]
```

输出：

```python
{
    (1, 2): 2,
    (2, 1): 1,
    (2, 3): 1,
}
```

出现次数最多的相邻对可以这样取得：

```python
pair = max(stats, key=stats.get)
```

注意：BPE 统计的是**相邻 token 对**，而不是任意两个 token 的共同出现次数。

---

## 6. 第二步：执行一次合并

```python
def merge(ids, pair, new_id):
    out = []
    i = 0

    while i < len(ids):
        can_merge = (
            i < len(ids) - 1
            and ids[i] == pair[0]
            and ids[i + 1] == pair[1]
        )

        if can_merge:
            out.append(new_id)
            i += 2
        else:
            out.append(ids[i])
            i += 1

    return out
```

例如：

```python
merge([5, 6, 6, 7, 9, 1], (6, 7), 99)
# [5, 6, 99, 9, 1]
```

实现时要特别注意：

- 检查 `i + 1` 前必须防止越界；
- 匹配成功后指针前进 2；
- 匹配的是不重叠相邻对；
- 不应在原列表上边遍历边修改。

---

## 7. 第三步：训练完整 BPE 词表

```python
def train_bpe(text, vocab_size):
    if vocab_size < 256:
        raise ValueError("vocab_size must be at least 256")

    ids = list(text.encode("utf-8"))
    merges = {}
    num_merges = vocab_size - 256

    for i in range(num_merges):
        stats = get_stats(ids)
        if not stats:
            break

        pair = max(stats, key=stats.get)
        new_id = 256 + i
        ids = merge(ids, pair, new_id)
        merges[pair] = new_id

    return merges
```

训练结果的关键参数是：

```python
merges: dict[tuple[int, int], int]
```

例如：

```python
{
    (101, 32): 256,
    (116, 104): 257,
    (257, 101): 258,
}
```

这表示：

```text
token 256 = byte 101 + byte 32
token 257 = byte 116 + byte 104
token 258 = token 257 + byte 101
```

第三条规则依赖第二条规则，所以合并顺序是模型参数的一部分，不能打乱。

### 7.1 压缩率

可用下面的指标衡量分词器对某段文本的压缩程度：

$$
\text{compression ratio}
=\frac{\text{原始字节数}}{\text{BPE token 数}}
$$

压缩率越高，同一个上下文窗口能装下的原始文本通常越多。但这并不意味着词表应无限增大，因为更大的词表会带来其他成本。

---

## 8. BPE 形成的是一片二叉树森林

每个原始字节都是叶子节点，每次合并创建一个父节点：

```text
        token 260
        /       \
   token 257   byte 101
    /    \
byte 116 byte 104
```

词表中会存在许多互不相连或局部相连的树，因此更准确的结构是“森林”。

这个心智模型解释了两件事：

1. 解码时需要递归或按训练顺序恢复每个 token 对应的字节；
2. 编码时必须先完成低层合并，才可能触发依赖它的高层合并。

---

## 9. 构造词表并实现解码

### 9.1 从合并规则恢复词表

```python
def build_vocab(merges):
    vocab = {i: bytes([i]) for i in range(256)}

    for (left, right), new_id in merges.items():
        vocab[new_id] = vocab[left] + vocab[right]

    return vocab
```

这里要求字典以合并创建顺序迭代。现代 Python 会保留字典插入顺序，但更稳妥的序列化格式应明确保存 merge rank。

### 9.2 解码

```python
def decode(ids, vocab):
    raw = b"".join(vocab[token_id] for token_id in ids)
    return raw.decode("utf-8", errors="replace")
```

流程是：

```text
token ID
  ↓ vocab 查表
每个 token 对应的 bytes
  ↓ 拼接
完整字节流
  ↓ UTF-8 解码
Python 字符串
```

### 9.3 为什么使用 `errors="replace"`？

任意 token 序列不一定构成有效 UTF-8。例如，一个多字节字符可能只生成了中间某个字节。严格解码会抛出异常：

```python
raw.decode("utf-8", errors="strict")
```

容错解码会用替换字符 `�` 标记无效片段：

```python
raw.decode("utf-8", errors="replace")
```

如果生成文本中出现 `�`，通常意味着模型输出了不完整或非法的 UTF-8 token 组合。

---

## 10. 实现编码：按合并优先级执行

训练时，越早创建的合并规则优先级越高。编码新文本时，必须优先应用 rank 最小的可用规则：

```python
def encode(text, merges):
    ids = list(text.encode("utf-8"))

    while len(ids) >= 2:
        stats = get_stats(ids)

        pair = min(
            stats,
            key=lambda p: merges.get(p, float("inf")),
        )

        if pair not in merges:
            break

        ids = merge(ids, pair, merges[pair])

    return ids
```

关键不是某对在待编码文本中出现多少次，而是：

> 当前所有可合并相邻对中，哪一对在训练阶段最早被创建？

若所有相邻对都不在 `merges` 中，最小 rank 会退化为无穷大，此时必须退出循环。

### 10.1 空字符串与单 token 边界

以下输入没有相邻对：

```python
""
"a"
```

所以编码循环应以 `len(ids) >= 2` 为前提，避免对空字典调用 `min()`。

### 10.2 朴素实现的性能

上述版本每轮都重新统计整个序列，便于学习和验证，但处理大规模语料时效率较低。生产实现通常会：

- 使用更高效的数据结构维护相邻关系；
- 并行处理独立文本块；
- 用 Rust、C++ 等实现热点路径；
- 对常用结果做缓存；
- 避免每次合并完整扫描序列。

## 11. 分词器训练与模型训练必须分开理解

### 11.1 分词器训练

输入是代表性文本，目标是得到：

- 合并规则及其 rank；
- token ID 到字节的词表；
- 正则预分块规则；
- 特殊 token 定义；
- 规范化和字节回退策略。

它不使用反向传播，也不训练 Transformer 参数。

### 11.2 语言模型训练

分词器固定后，用它把海量原始文本转换为 token ID。语言模型读取这些 ID，学习预测下一个 token。

```text
分词器训练语料 ──BPE──> 固定分词器
                           ↓
模型训练语料 ──encode──> token 数据集 ──反向传播──> 模型参数
```

一旦模型开始训练，分词器通常就被冻结。训练中途更换 token ID 语义，会让已经学到的 Embedding 和输出权重失效。

### 11.3 为什么两套训练语料需要协调？

分词语料的组成决定哪些模式会获得独立 token：

- 英文占比高，会形成更多英文词片段；
- 中文、韩文等占比低，文本可能被拆成更多 token；
- 代码占比高，会形成常见关键字、缩进和符号模式；
- 某种结构化格式占比高，会提高该格式的 token 密度。

如果一个 token 在分词语料中很常见，却在模型训练语料中几乎不出现，那么它虽然进入了词表，对应 Embedding 却可能基本没有被训练。推理时触发这类 token，可能产生异常输出。

---

## 12. 为什么还需要正则预分块？

朴素 BPE 允许任意相邻字节跨边界合并，可能形成不理想的超长 token。实际分词器通常先用正则表达式把文本切成片段，再在每个片段内部独立执行 BPE：

```text
原始文本
  ↓ 正则预分块
缩写 | 字母串 | 数字串 | 标点 | 空白
  ↓ 每块独立执行 BPE
token ID 序列
```

预分块规则可以控制：

- 是否把前导空格与单词放在同一块；
- 缩写形式如何处理；
- 大小写是否共享同类规则；
- 数字最多按几位一组；
- 标点能否与字母跨界合并；
- 连续空格是否能够合并。

它本质上是在 BPE 之上添加“哪些边界永远不能跨越”的先验。

### 12.1 前导空格为何经常属于 token？

很多字节级分词器会把空格与后面的单词片段组合：

```text
"hello"  与  " hello"
```

二者可能得到完全不同的 token ID。这样做能高效表示自然语言中常见的“空格 + 单词”，但也会造成：

- 句首单词和句中单词表示不同；
- 尾随空格改变后续分词；
- 截断在 token 内部时，补全行为变得不稳定。

### 12.2 数字分块

如果数字完全由统计合并，整数可能被随机拆成 1 位、2 位、3 位或更长片段，不利于按位运算。现代规则常限制数字块长度，使数字分解更规律。

### 12.3 代码与连续空格

旧式规则可能让每个缩进空格都成为独立 token，大量浪费上下文。更合理的规则允许多个连续空格合并，从而提高代码密度。

## 13. 特殊 token

特殊 token 用来表达普通文本之外的结构，例如：

- 文档结束；
- 序列开始与结束；
- 消息起点与终点；
- 用户、助手和工具角色；
- 填充位置；
- 中间填充任务的前缀、后缀和中部边界。

它们通常不经过普通 BPE，而是由编码器提前识别并直接替换成预留 ID：

```text
普通文本 ──BPE──> 普通 token
特殊标记 ──直接映射──> 特殊 token ID
```

### 13.1 特殊 token 的安全边界

编码不可信输入时，必须明确决定：

- 哪些特殊 token 允许被解析；
- 哪些字符串只能作为普通文本；
- 用户输入是否可能伪造系统边界；
- 解码后是否会再次被其他组件解释。

若把用户可控文本误识别为控制 token，就可能破坏消息结构、提前终止生成或形成注入面。

### 13.2 增加特殊 token 需要模型同步扩容

假设词表由 $V$ 扩展到 $V+k$，至少要修改：

```text
输入 Embedding：  (V, C) → (V+k, C)
输出 LM Head：     (C, V) → (C, V+k)
输出 bias（若有）：(V,)   → (V+k,)
```

新增行通常随机初始化，因此还要用包含这些 token 的数据继续训练，否则模型并不知道它们的语义和用法。

## 14. 两类常见实现路线

### 14.1 字节级正则 BPE

典型流程：

```text
Unicode 字符串
  ↓ UTF-8
字节
  ↓ 正则预分块
独立字节块
  ↓ BPE
token ID
```

特点：

- 原始词表固定包含 256 个字节；
- 任意文本都可编码；
- 逻辑较统一；
- 高性能库通常擅长推理编码，但未必提供词表训练功能。

### 14.2 码点级分词加字节回退

另一种常见路线直接在 Unicode 码点或文本片段上训练 BPE/Unigram，并提供：

- 字符覆盖率控制；
- 未知 token；
- 字节回退；
- 虚拟前导空格；
- 归一化规则；
- 训练和推理一体化。

如果训练时没见过某个罕见码点：

- 没有字节回退时，它会变成统一的未知 token，丢失原始信息；
- 开启字节回退后，它会转为 UTF-8 字节 token，仍可无损恢复。

字节回退通常更适合开放世界文本，但配置项之间可能相互影响，必须逐项验证。

### 14.3 虚拟前导空格

有些实现会在每条文本开头自动添加一个空格，使句首单词和句中单词更可能采用相同切分：

```text
"world"       → " world"
"hello world" → 保持 " world"
```

这能减少位置导致的词形分裂，但也改变了输入规范，编码和解码必须一致处理。

## 15. 词表大小如何选择？

词表大小不是越大越好，而是需要平衡。

### 15.1 大词表的优点

- 同一文本需要更少 token；
- 固定上下文窗口能覆盖更多原始字符；
- 常见词、短语、代码片段可直接表示；
- 推理步骤数可能减少。

### 15.2 大词表的成本

- Token Embedding 参数量增大；
- 输出 LM Head 参数量增大；
- 每一步要计算更多类别的 logits；
- 每个 token 出现频率降低，更容易训练不足；
- 过长片段被压成一个 token，字符级结构更难访问；
- 增加模型文件大小和显存占用。

假设 embedding 维度为 $C$，不考虑权重绑定时，词表相关参数约为：

$$
V\times C + C\times V = 2VC
$$

若输入 Embedding 与输出权重共享，则可减少一部分参数，但输出 Softmax 的类别数仍是 $V$。

### 15.3 小词表的优点与成本

小词表让每个 token 获得更多训练样本，输入和输出层也更轻；但序列更长，注意力成本更高，并会更快耗尽上下文窗口。

### 15.4 实际选择方法

词表大小通常通过实验决定，应同时观察：

- 多语言 token/字符比；
- 代码 token/字符比；
- 结构化数据 token/字符比；
- 训练吞吐与显存；
- 下游任务质量；
- 稀有 token 出现频率；
- Embedding 与输出层参数占比。

---

## 16. 分词如何影响模型能力？

### 16.1 拼写和字符操作

如果一个长单词整体是单个 token，模型直接看到的是一个整数，而不是内部字符。于是下列任务会变难：

- 统计某个字母出现次数；
- 反转字符串；
- 删除指定位置的字符；
- 按字符排序。

把字符串显式拆成带空格的单字符，往往能改善表现，因为每个字符更可能独立进入上下文。

### 16.2 整数运算

若数字切分不规律：

```text
127  → 一个 token
677  → 两个 token
804  → 另一种两段组合
```

按位加减法要跨越不一致的 token 边界，模型需要额外学习大量组合。更规则的数字预分块通常更有利于算术。

### 16.3 多语言差异

如果分词训练集偏向英语，同样语义在其他语言中可能需要数倍 token：

```text
更长的 token 序列
  ↓
更快耗尽上下文窗口
  ↓
注意力计算更多
  ↓
单位文本成本更高
```

所以多语言能力不仅取决于模型训练数据，也取决于分词训练数据。

### 16.4 代码能力

代码含有大量：

- 连续空格；
- 换行与缩进；
- 标点组合；
- 常见关键字；
- 重复语法结构。

若缩进被逐空格拆分，短程序也会占用大量 token。专门优化空白与代码模式的分词规则，可以显著提高有效上下文密度。

### 16.5 结构化格式

表达同一数据的不同格式可能产生不同 token 数。选择格式时，除了可读性和生态兼容性，也应实测 token 密度，而不是仅比较字符数。

---

## 17. 尾随空格与不稳定 token

很多分词器把前导空格包含在后面的 token 中：

```text
" word" → 一个常见 token
```

如果提示末尾提前放入空格：

```text
"... word "
```

这个空格可能被单独编码，而模型训练时更常见的是它与下一个词共同组成 token。输入因此落到罕见分布，补全质量可能下降。

更一般地，如果字符串恰好截断在一个常见 token 的内部，继续补全就不能简单理解为“在现有 token 序列后追加下一个 token”。字符级补全与 token 级补全之间会出现边界错位。

工程上应注意：

- 避免无意的尾随空格；
- 流式输入不要随意截断 UTF-8 或 token；
- 补全接口需要专门处理不稳定前缀；
- 缓存键必须以实际 token 序列为准；
- 测试各种空格、换行、制表符和部分单词前缀。

---

## 18. 分词器也是安全边界

分词错误不只影响质量，也可能影响安全：

### 18.1 控制 token 注入

用户文本若能被解释为消息边界或结束标记，可能改变上层协议结构。

### 18.2 未训练 token

词表中的某些 token 若在模型训练中从未出现，其 Embedding 近似随机。输入这些 token 相当于向网络注入未训练向量，行为不可预测。

### 18.3 规范化差异

视觉上相似的字符、不同 Unicode 组合形式或不可见字符，可能得到完全不同的 token 序列。安全过滤若在字符串层执行，而模型在另一种规范化结果上工作，就可能产生绕过。

### 18.4 编解码不一致

不同组件若使用不同版本的词表、正则规则或特殊 token 配置，同一文本会被解释成不同 ID，造成协议混乱。

因此，生产系统应把下列内容进行版本化并作为一个整体发布：

```text
词表 + merge ranks + 正则规则 + 特殊 token + 规范化规则
```

---

## 19. 新增 token 与模型手术

为已训练模型增加 token 时，可以：

1. 扩展输入 Embedding；
2. 扩展输出语言模型头；
3. 初始化新增参数；
4. 冻结或部分冻结原模型；
5. 使用包含新 token 的数据训练新增参数；
6. 检查旧 token 行为是否回归。

除了结构控制 token，还可以学习少量“压缩 token”：冻结主体模型，只优化新 token 的 embedding，使少数新 token 近似代替一段很长的固定提示。这说明 token 不仅能代表文本片段，也能作为可学习的软接口。

同一思想还能扩展到其他模态：先把图像、音频或连续信号压缩为离散 token 或连续 patch 表示，再交给统一的序列模型处理。核心模型未必需要改变，变化主要发生在各模态的编码和解码端。

## 20. 最小可用 Tokenizer 类

```python
class BasicTokenizer:
    def __init__(self):
        self.merges = {}
        self.vocab = {i: bytes([i]) for i in range(256)}

    def train(self, text, vocab_size):
        ids = list(text.encode("utf-8"))
        num_merges = vocab_size - 256

        for i in range(num_merges):
            stats = get_stats(ids)
            if not stats:
                break

            pair = max(stats, key=stats.get)
            new_id = 256 + i
            ids = merge(ids, pair, new_id)
            self.merges[pair] = new_id

        self.vocab = build_vocab(self.merges)

    def encode(self, text):
        ids = list(text.encode("utf-8"))

        while len(ids) >= 2:
            stats = get_stats(ids)
            pair = min(
                stats,
                key=lambda p: self.merges.get(p, float("inf")),
            )

            if pair not in self.merges:
                break

            ids = merge(ids, pair, self.merges[pair])

        return ids

    def decode(self, ids):
        raw = b"".join(self.vocab[i] for i in ids)
        return raw.decode("utf-8", errors="replace")
```

这是教学用最小实现。生产版本还需要：

- 正则预分块；
- 特殊 token；
- 文件保存与加载；
- 严格版本检查；
- 更快的训练与编码算法；
- 并行和缓存；
- 完整错误处理；
- 多语言与恶意输入测试。

## 21. 必做测试

### 21.1 往返一致性

```python
assert tok.decode(tok.encode("hello")) == "hello"
assert tok.decode(tok.encode("你好🙂")) == "你好🙂"
assert tok.decode(tok.encode("")) == ""
```

### 21.2 训练集外文本

不要只测试训练语料，还应覆盖：

- 未见过的语言；
- 罕见 Unicode；
- 表情与组合字符；
- 代码；
- 很长空白；
- 制表符与换行；
- 二进制式控制字符；
- 空字符串和单字符。

### 21.3 合并优先级

构造存在多种可合并路径的例子，确认编码始终选择 rank 最小的规则。

### 21.4 非法 token 序列

确认解码无效 UTF-8 时不会导致服务崩溃，并明确采用严格报错还是替换策略。

### 21.5 保存与加载

序列化后重新加载，必须得到完全相同的：

```text
encode 结果
decode 结果
merge rank
特殊 token ID
```

### 21.6 与目标实现对齐

若要复用现有模型，不能只保证“能无损还原文本”，还必须逐 token 完全一致。相同文本只要产生一个不同 ID，就无法直接使用原模型的 Embedding。

## 22. 常见错误清单

### 22.1 把 Unicode 码点当作 UTF-8 字节

码点可能远大于 255，而字节一定在 `0～255`。

### 22.2 训练和编码使用不同规则

训练时有正则分块、编码时没有，或者特殊 token 配置不一致，都会产生错误结果。

### 22.3 编码时选择最高频 pair

最高频只用于训练阶段。推理编码应选择训练 rank 最小的可用 pair。

### 22.4 打乱 merges 顺序

后期合并可能依赖早期 token，顺序变化会让词表含义改变。

### 22.5 忽略空输入

空字符串和单字节输入没有 pair，必须提前返回。

### 22.6 假设任意 token 都能独立解码

一个 token 可能只是多字节字符的一部分，单独解码会失败。

### 22.7 只在英文上衡量压缩率

英文表现好不代表中文、代码、数学和结构化数据也高效。

### 22.8 新增 token 后不训练模型

扩展矩阵只能让维度匹配，随机初始化的 token 向量并不自动拥有语义。

### 22.9 允许用户任意触发特殊 token

这可能破坏角色边界、文档边界或终止逻辑。

## 23. 动手实现路线

建议按以下顺序推进：

1. 将字符串转换为 UTF-8 字节列表；
2. 实现 `get_stats()`；
3. 实现单次 `merge()`；

7. 按 merge rank 实现 `encode()`；

12. 与目标分词器逐 ID 对比；
13. 测量多语言、代码与结构化格式的 token 密度；

每一步都应保持可运行和可测试，避免同时处理算法、性能、特殊 token 与文件格式。

## 25. 最终心智模型

可以把 GPT 分词器压缩成下面五层：

```text
第 1 层：Unicode 定义人类看到的字符
第 2 层：UTF-8 把字符稳定地转换为字节
第 3 层：BPE 把高频相邻字节压缩成 token
第 4 层：正则和特殊 token 为压缩过程加入结构规则
第 5 层：模型只看到最终 token ID，并学习它们之间的关系
```

分词不是无关紧要的数据清洗，而是在决定模型的“基本原子”。它影响一段文本需要多少计算、模型能看多远、哪些模式容易学习、哪些字符任务困难，以及哪些输入可能成为安全边界。

一个可靠的分词器需要同时满足四个目标：

```text
完备：任意文本都能编码
可逆：正常文本能够无损还原
高效：常见数据使用尽量少的 token
一致：训练、推理和所有组件使用完全相同的规则
```

真正需要掌握的核心链路是：**Unicode → UTF-8 字节 → BPE merges → token ID → Embedding**。理解这条链路后，许多看似来自模型本身的怪异行为，就能从分词边界、词表统计和训练分布中得到解释。
