# Dense Transformers and Mixture-of-Experts (MoE)

> The differences between Dense and MoE mainly occur in the FFN sublayer of Transformer. This article first analyzes the general mechanisms, training difficulties and deployment economics in the industry, and finally uses miniLLM to make a brief mapping.

## 1. Catch the difference in one sentence

- **Dense**: Each token uses the same set of FFN parameters, and the total parameters grow basically synchronously with the activation parameters of each token.
- **Sparse MoE**: Prepare multiple groups of Experts, and only a few of them will be activated by router for each token, so that the total parameter capacity and the single token compute are partially decoupled.

The core value of MoE is not "free computing", but to exchange routing, GPU memory and communication complexity for greater parameter capacity.

## 2. What do the two architectures share?

Dense and MoE usually share the same Decoder trunk:

```text
embedding
  -> RMSNorm
  -> Causal attention (MHA/GQA/MLA)
  -> Residual
  -> RMSNorm
-> Dense FFN or Sparse MoE
  -> Residual
```

Therefore, RoPE, GQA, KV Cache, FlashAttention and MoE do not conflict. MoE solves the capacity problem of token internal channel transformation, and attention solves the information interaction between tokens.

## 3. How does Dense FFN work?

Take SwiGLU as an example:

\[
\operatorname{FFN}(x)=W_o\left(\operatorname{SiLU}(W_gx)\odot W_ux\right)
\]

When the input dimension is \(d\) and the intermediate dimension is \(d_{ff}\), the parameter amount of ignoring Bias is about:

\[
P_{dense}\approx 3dd_{ff}
\]

Advantages of Dense:

- Each token updates all FFN parameters, and the sample utilization is stable;
- Calculate chart rules, suitable for high-efficiency GEMM;
- No need for token routing and All-to-All;
- It is usually easier to achieve high utilization when single GPU, small batch, and low concurrency;
- The debugging, quantification and deployment path are mature.

Its price is: when you want to increase the knowledge capacity, it usually increases each token FLOPs and inference latency.

## 4. The complete data stream of Sparse MoE

Assuming that there are \(E\) Experts, each token activates \(K\).

### 4.1 router Score

\[
r(x)=W_rx,\qquad p(x)=\operatorname{softmax}(r(x))
\]

router outputs token's preferences for each expert.

### 4.2 Top-K Selection

\[
S(x)=\operatorname{TopK}(p(x),K)
\]

Only execute the expert in the set \(S(x)\). Top-1 path is more computational; Top-2 or higher K can integrate multiple Experts, but increase computing and communication.

### 4.3 Dispatch, expert Calculation and Combine

The system rearrands token according to the expert, sends the token to the device where the expert is located, executes FFN respectively, and then sends the result back to the original location:

\[
y=\sum_{i\in S(x)}\tilde p_i(x)E_i(x)
\]

The bottleneck of large-scale MoE is often not in the formula, but in token sorting, capacity limitation, All-to-All, load unevenness and small matrix efficiency.

## 5. Total parameters, activation parameters and FLOPs must be separated.

If each expert is equal to Dense FFN, the total parameters of MoE FFN are about:

\[
P_{total}\approx E\cdot 3dd_{ff}
\]

The activation parameters of each token are about:

\[
P_{active/token}\approx K\cdot 3dd_{ff}
\]

But the actual cost also includes:

- All expert weights still need to be stored or fragmented;
- The expense of router, Dispatch and Combine;
- Cross-device All-to-All communication;
- Invalid calculations generated by Padding to expert Capacity;
- expert batch is too small, resulting in a decrease in hardware utilization.

Therefore, the description of the calculation path of "37B activation parameters" does not mean that the model only needs to store 37B parameters.

## 6. Load balancing: the most core training problem of MoE

If a few Experts are frequently selected, there will be:

- Hot expert overflows, loses token or queues up;
- Cold Door expert Lacks Gradient, Forming A Route Collapse;
- The workload of different devices is uneven, and the throughput is limited by the slowest device.

### 6.1 Auxiliary load balancing loss

The classic practice constrains the reception ratio and the average routing probability of expert at the same time. The intuitive goal is to make the two close to uniform distribution:

\[
L=L_{LM}+\lambda L_{balance}
\]

\(\lambda\) is too small to balance, and too large to interfere with the language modeling goal.

### 6.2 Auxiliary-loss-free Balancing

Another route is not to add a strong equilibrium gradient to the main loss, but to maintain the bias updated by expert on the routing score, so as to reduce the selection probability of overload expert. The public report of DeepSeek-V3 adopts this method.

### 6.3 Capacity and token Dropping

Each expert's permanent capacity limit:

\[
C\approx \left\lceil\frac{N\cdot K}{E}\cdot \text{capacity factor}\right\rceil
\]

tokens that exceed the capacity can be discarded, transferred to alternative expert, or processed through no-discard scheduling. Training throughput, model quality and implementation complexity need to be weighed together.

## 7. The mainstream evolution of expert structure

### 7.1 Routed expert and Shared expert

Shared expert activates all tokens and undertakes general knowledge; Routed expert learns more conditional patterns. This can reduce the problem that all general-purpose capabilities are forced to be repeatedly deposited into each expert.

### 7.2 Fine-grained expert

Disassembling a small number of large Experts into more small Experts can make the combination more flexible and maintain a similar activation width. But the finer the expert, the more complex the routing metadata and communication scheduling.

### 7.3 Each layer MoE and staggered MoE

Not every Block must use MoE. The staggering of the Dense layer and the MoE layer can reduce the burden of communication and deployment; the public architecture of Llama 4 is one of these combined ideas.

### 7.4 expert Parallel

Different devices save different Experts. token is exchanged across devices according to the routing results, which is the key to expanding the total parameters and also makes the network topology a part of the model architecture.

## 8. Why MoE may learn "expertization", but can't take it for granted?

router will select expert according to the hidden state, so expert may form preferences for language, code, syntax or abstract features. But real expertization is usually not a clear division of labor pre-named by human beings.

Judging the expert should look at the evidence:

- expert usage distribution of different data domains;
- Mutual information of token type and routing;
- Changes in ability after shielding or replacing an expert;
- Cross-layer routing stability;
- expert represents similarity and gradient similarity.

Just looking at which expert token is divided into a few examples, it cannot prove that the semantic expertization is.

## 9. Fair comparison between Dense and MoE

At least one comparison caliber should be fixed:

| Compare the caliber | Fixed item | Questions suitable for answer |
|---|---|---|
| Wait for training FLOPs | token number, total training calculation | Who has higher quality under the same budget |
| Wait for activation parameters | Calculation scale per token | Whether the sparse capacity is valid |
| and other total parameters | model storage scale | who is more efficient with the same weight capacity |
| Equivalent memory | Equipment and peak memory | What can be trained/deployed by the actual hardware |
| Waiting for delay/throughput | Reasoning framework and concurrency | Which online service is more cost-effective |

It is necessary to record language model loss, downstream capacity, token/s, MFU, peak GPU memory, All-to-All time, expert load discreteness and failure rate at the same time.

## 10. Typical failure mode of training and deployment

### 10.1 router Collapse

The symptoms are a small number of expert long-term overload. The processing direction includes equalization mechanism, router initialization, routing temperature, capacity and data mixing.

### 10.2 expert Lack of learning

When the total number of tokens remains unchanged, a single expert may see fewer samples. Small data and small batch scenarios are especially prone to "more parameters but not thoroughly trained".

### 10.3 Communication Flooding Calculation

When the expert is too small or the single GPU/single node division is unreasonable, the All-to-All expense may exceed the saved FFN calculation.

### 10.4 Low concurrency efficiency on the line is poor

The expert batch generated by a single request is very small, and it is difficult for the sparse GEMM to fill the GPU. High-throughput service and end-side low latency may lead to completely different architectural options.

### 10.5 Quantification and deployment fragmentation

The access frequency of different Experts is inconsistent, and weight scheduling and quantitative calibration are more difficult than Dense; the total weight may also span more devices.

## 11. What do you think of the public route in the industry?

| Route | Representative | Observable Key Points |
|---|---|---|
| Large-scale Dense | Llama 3 etc. | Data scale, training stability, deployment ecology |
| Classic Top-K MoE | Switch Transformer, GShard | Capacity Control, Balanced Loss, expert Parallel |
| Shared + Routed expert | Mixtral, DeepSeekMoE, Llama 4 | General Path and Conditional Capacity Combination |
| Fine-grained MoE | DeepSeek-V2/V3 | More Small expert, Less Activation, Communication Collaborative Design |
| Hybrid Dense/MoE layer | A variety of new generation models | Use staggered structures to compromise quality, communication and delay |

These lines show that Dense and MoE will coexist for a long time. Dense is a reliable baseline, and MoE is an important means of expansion when the scale is large enough and the system capability is strong enough.

## 12. How to choose Dense or MoE

Typical conditions of priority Dense:

- The model and data are relatively small;
- single GPU or low-bandwidth interconnection;
- Pursue low concurrency, stable delay or end-side deployment;
- A credible training and evaluation baseline has not been established;
- The team is not ready to maintain the special MoE kernel and monitoring.

Consider the typical conditions of MoE:

- Want to increase the total parameter capacity but control each token FLOPs;
- There are enough tokens to train multiple Experts;
- With high-speed interconnection and mature expert Parallel;
- It can continuously monitor routing, capacity, communication and expert degradation;
- Online throughput can dilute and sparse scheduling costs.

## 13. Dense/MoE mapping of miniLLM

miniLLM can switch between `MiniLLMMLP` and `MiniLLMSparseMoE` under the premise that the attention trunk remains unchanged. The default MoE configuration is 4 Experts, each token Top-1, and the auxiliary load balancing loss is used; router is calculated by float32, only for valid token routes.

Special attention should be paid to: When the Top-1 selection probability is re-reorganized, the unique weight will become 1. Therefore, router mainly learns through "who is selected" and auxiliary loss, and the main task loss will no longer provide the same gradient signal through continuous gate weight. This property is very suitable for `norm_topk_prob` ablation.

miniLLM does not have expert Parallel, Shared expert, Capacity/token Dropping, and no production-level sparse kernel. Therefore, it is suitable for answering "whether the MoE algorithm is correct and whether it is better than Dense under the same training budget", and it is not suitable for inferring the service efficiency of industrial-level MoE by single-card speed.
